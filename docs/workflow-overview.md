# GameCreator 全 AI 开发工作流

AI 以引擎工程为主要工作目录，通过实际运行效果验证设计。GameCreator 项目保存正式需求、规范、分工、排期与验收记录，两边通过设计提交、工程同步、数据同步和开发反馈持续更新。

这份总览说明谁在什么位置工作、成果如何进入下一步。具体按钮、提交命令和格式请查阅“操作说明”；内容组织与兼容要求请查阅“通用规范”。

## 先分清三个目录

### GameCreator 软件目录

这里是管理工具本身的程序代码。只有开发或修复 GameCreator 时才需要修改；日常制作游戏不在这里编写游戏内容。

### GameCreator 项目目录

这里保存当前游戏的设计、配置、任务、授权和处理记录，以 project.gamecreator 为项目入口。

根目录的 GAMECREATOR_GUIDE.md 是使用说明，PROJECT_STANDARDS.md 包含通用规则与本项目约定。ai/README.md 是设计编写入口，ai/context/ 提供当前内容，ai/changes/ 接收设计提交，ai/receipts/ 保存处理回执。

正式存档由 GameCreator 管理。AI 通过校验与签名提交修改内容，不直接改写 archives、锁文件或只读上下文。

### 引擎工程目录

这里保存实际游戏代码、场景、美术、音频与测试成果，是制作人、策划、程序、美术、测试等 AI 的主要工作目录。

默认从 gamecreator/README.md 进入协作流程，从 docs/gamecreator/ 阅读同步后的设计文档。引擎中的 Markdown 是查阅副本，直接修改它们不会回写 GameCreator。

## 1. 准备项目与开发者

管理者先在 GameCreator 创建项目并保存为独立文件夹，再在“项目管理 → 工程连接”选择引擎类型，保存实际工程根目录。

在“人员分配”定义岗位职责，再创建 AI 开发者身份和长期令牌。岗位描述需要做什么，开发者承担具体工作；一个开发者可以承担多个岗位，同一岗位也可以由多个开发者分工。

至少准备一位启用的制作人，具有制作管理岗位、项目范围、项目内容写入权限和对应模块授权。制作人可以暂时没有具体任务，后续分配工作无需更换身份。

为其他开发者设置名称、职责、岗位、任务范围和反馈权限。令牌用于识别提交者和核验授权，不会自动启动 AI、执行任务或授予文件系统权限。每位 AI 使用分配给自己的凭证。

## 2. 同步协作入口与成员凭证

在“项目管理 → 工程同步”检查引擎位置、成员凭证、协作入口目录和文档目录。启用的开发者需要有效长期令牌及本机可读取的凭证；缺失凭证时先导入已保存凭证或更换令牌。

在同步配置中开启开发协作和成员凭证同步，保存后预览变更，检查新增、更新、冲突和待移除内容，处理后同步到工程。首次同步和后续更新使用同一入口。默认输出位置如下，实际以同步配置中保存的路径为准：

```text
引擎工程/
  gamecreator/
    README.md          工作流入口及绑定的 GameCreator 项目位置
    personal/          各开发者的私有凭证，按成员 ID 命名
    project.json       项目身份与公开上下文信息
    context/           当前任务、分工及开发反馈比较基准
    feedback/          开发者提交的反馈
    receipts/          开发反馈处理回执
  docs/gamecreator/
    README.md          分类文档索引
    modules/           按类别组织的设计文档与本项目自定义规范
```

如果协作入口设为其他子目录，入口 README 和 personal/ 会放到该目录，开发反馈仍使用固定的 gamecreator/feedback/。

开启成员凭证同步后也会刷新绑定的 GameCreator 项目中的使用说明、完整规范和 ai/ 编写上下文。它准备协作环境，不启动引擎、不自动创建游戏场景，也不自动签发新的开发者身份。

personal/ 保存私有凭证，凭证同步会添加相应忽略规则。凭证不放入公共文档、反馈文件或版本库；该文件夹本身不提供成员之间的访问隔离。

使用软件级 MCP 时，在左侧底部“MCP 连接”添加项目与开发者连接，复制统一客户端配置。助手调用 gc_connections 后，核对接入码并授权该会话，再由助手逐次明确指定 connectionId。软件本地凭证库负责签名，无需把私钥填入客户端配置。会话是适配器进程；不同岗位需要独立进程并分别授权，详见使用帮助的“AI 工作流工具”。

## 3. 制作人和策划建立设计与计划

AI 先阅读引擎入口 README，核对项目身份、两边目录、当前引擎内容和项目约定。需要设计或调整方案时，进入绑定的 GameCreator 项目，阅读使用说明和最新内容快照。

从零设计先明确目标、版本范围和验收标准，再组织玩法核心、玩法文档、原型、功能系统、配置、素材标准、开发工具，以及任务和里程碑。已有项目先检查可复用的分类、模块与稳定 ID，说明本次复用、修改、新增、归档的内容和影响。

在“项目管理 → 项目内容同步”更新协作文件后，AI 根据当前快照和模板编写变更批次，运行校验，使用自己的凭证签名，提交到 GameCreator 项目的 ai/changes/。

设计编写可以通过文件和命令完成，不要求逐项操作界面填写。新增内容保持初始制作状态，写完设计文档不代表功能已实现或已验收。

## 4. 检查并应用设计提交

管理者在“项目内容同步 → 设计提交”读取提交，检查差异、权限、引用关系和兼容方案，解决冲突后应用。

客户端在应用时再次校验最新内容和授权；过期快照或并发修改需要重新比较。应用成功后才写入 GameCreator 正式项目，AI 可通过该项目的 ai/receipts/ 确认结果。

设计提交的读取、预览和应用可以通过已授权的 MCP 工具或客户端执行；签名提交不会自动应用。开发反馈与里程碑验收仍使用现有处理入口。

## 5. 将正式设计同步到引擎

设计应用后，通过“工程同步”预览并同步最新设计文档、项目自定义规范、任务与协作上下文，让开发者按已确认的要求继续工作。

引擎保留当前项目的自定义规范；完整通用规则与 GameCreator 使用说明保存在管理项目，由入口 README 指向其位置。

### 三种同步入口的分工

项目内容同步：读取 AI 对设计与计划的内容提交，检查后写入 GameCreator 项目。提交位置是管理项目的 ai/changes/。

工程同步：将设计文档和协作上下文送到引擎，同时读取、处理引擎中的开发反馈。反馈位置是引擎的 gamecreator/feedback/。

数据同步：处理实际配置 JSON 的导入、导出和冲突。例如配置目录为 data/generated/ 时，pvz_plants.json 对应 pvz_plants 表。同步配置文件与同步配置说明文档是两个不同操作。

两套提交使用各自的快照、格式和回执，不能把设计批次放到反馈目录，也不能把开发反馈当作设计批次处理。

### 正式制作前的交接

制作人将已应用设计、任务 ID、依赖、允许修改范围、交付位置、验收步骤和反馈方式整理为工作包，交给对应执行助手，并确认接手结果。创建成员、签发令牌和分配任务不等于实际助手已开始工作。未接入执行助手时，报告“待接入执行助手”及所缺条件，继续推进其他管理工作；不自行代做，也不自动提高任务状态。

制作人默认组织开发，可以阅读工程、运行已有原型、检查证据。项目范围和管理权限不等于程序、美术等岗位的执行授权。需要兼任时，由用户或有权管理者明确授权，登记对应岗位、权限及具体任务；不得自行扩权或借用其他成员凭证。详细约定见“制作人与团队管理”。

## 6. 各岗位在引擎中制作与验证

程序实现功能、场景逻辑与开发工具；美术按照已确认风格和规格制作资源；音效完成声音内容与接入；测试检查功能、体验和回归结果。

制作人、策划和主美同样结合引擎中的实际表现判断设计是否成立。开发者先读取分配范围、前置依赖和验收要求，再进行实现，记录运行入口、交付路径和验证证据。

美术资源直接在引擎工程中生成和接入。GameCreator 保存制作要求、风格标准、工程交付位置与状态，无需把图片导回管理项目才能确认完成。

## 7. 提交开发反馈，更新进度

开发者使用自己的凭证，将进度、开发结果、交付路径、测试依据和剩余问题提交到引擎的 gamecreator/feedback/。管理者在“工程同步 → 开发反馈”处理，结果写入 GameCreator，回执保存在引擎的 gamecreator/receipts/。

开始工作时报告“进行中”；实现完成并附上验证结果后报告“待验收”；无法继续时报告“受阻”并说明原因。通过验收确认后，任务才进入“已完成”。

明确关联到任务的素材与开发工具，按相关任务的汇总情况更新状态，不根据名称相似自动关联，也不因其中一项完成就把全部成果标记完成。

### 不同反馈表达什么

progress：报告做到了什么，包括进度、结果和受阻原因。

review：提交验收结论，需要对应的验收权限。

propose：提出分工或排期建议，当前作为任务建议记录，不直接改动计划。

spec_change：建议修改已有任务说明或验收标准，需要说明原因与影响，单独检查后采纳。

project_change：具有项目写入权限和对应范围的开发者提交正式项目内容修改。引擎反馈入口支持已有字段修改；新增、删除或跨模块重组使用管理项目的 ai/changes/ 内容批次。

无冲突且符合条件的普通反馈可以批量应用。需求变更、正式项目修改及冲突需要逐项检查，不能把一键应用当作跳过权限和验收的入口。

## 8. 验收与下一轮迭代

验收检查实际运行效果、交付文件和验证依据。有验收权限的开发者可以提交结论，管理者在客户端核实并确认。任务全部验收完成后，里程碑会提供确认入口，仍由管理者单独确认里程碑验收。

如果实现偏离已确认要求，修复实现；如果要求本身需要调整，提出需求或验收标准变更建议；如果涉及新增玩法、重组系统或多个模块，提交新的项目内容变更批次。

需求变化不会自动提升制作状态，也不能把代码当前行为直接当成验收标准。保留既有成果和验收历史，为新的工作建立或调整相应任务。

变更应用后，刷新 GameCreator 协作文件，再同步引擎文档、任务上下文和所需配置。所有开发者读取最新上下文，进入下一轮制作与验证。两边目录搬迁后，应更新工程连接和入口文档。

## 四个不能混淆的状态

已提交：变更或反馈文件已经生成，等待处理。

已应用：客户端已经检查并写入正式项目记录。

已实现：引擎中已有实际成果，需要说明测试情况和未完成项。

已验收：成果经过核实，满足约定的验收标准，并完成相应确认。

## 完整循环

```text
准备工程与开发者 → 同步协作入口 → 设计或调整方案
    → 提交并应用到 GameCreator → 同步文档与配置到引擎
    → 交付工作包并确认执行助手接手 → 各岗位开发与运行验证
    → 提交反馈并更新进度
    → 任务与里程碑验收 → 下一轮设计与开发
```

实际引擎效果为下一轮设计提供依据；正式需求、开发事实和验收结论分别记录，通过明确的提交与同步保持一致。

## 制作人如何从空项目开始

制作人接手后先检查引擎现状、用户目标和管理项目设计，形成最小玩法、范围、验收基线和制作计划；没有个人制作任务时主动完成设计、分工、交接、协调与验收，不默认承担程序、美术等制作任务。首次汇报应包含设计基线、团队职责与授权、任务依赖、验收要求以及提交和应用状态。

新建制作人默认具有独立的 `team_manage` 权限。管理项目更新协作文件后，`ai/TEAM_MANAGEMENT.md` 提供完整命令，`ai/manage-team.cjs` 可使用制作人自己的私有 JSON 凭证，直接创建程序、主美等开发者、签发长期令牌，以及持续调整多岗位和多任务分配。客户端须打开对应项目；已有身份需显式授予新权限，岗位名称本身不代表授权。

授权只能覆盖制作人当前拥有的能力与有效期。团队命令成功即生效，记录可在“开发者与令牌”查看；项目正文仍通过内容同步检查并应用。工作文档 Markdown 与私有凭证 JSON 分别交付；创建身份不等于自动启动外部 AI 助手。核对实际执行助手接手后，按引擎实际表现组织开发、反馈、验收和下一轮设计；未接入时交付工作包并说明缺口。

## AI 工作流工具入口

管理项目 ai/WORKFLOW_MCP.md 与使用帮助“AI 工作流工具”提供同一份说明。连接配置见 ai/mcp.config.example.json。制作人可依次调用读取、校验、提交、预览、应用、协作导出及工程同步工具；每个助手使用自己的长期凭证，按当前授权执行，并保留操作记录。
