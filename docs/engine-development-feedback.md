# 开发协作与进度回写

GameCreator 向引擎工程输出需求与任务上下文。开发者、AI 编程助手或编辑器工具在工程中提交结构化反馈，GameCreator 展示差异，由用户应用到项目排期、开发工具或已授权的项目内容。

这是一套引擎无关的文件协议。目前通过已有 Godot 4 / 绿洲启元工程连接使用，不需要单机游戏额外部署服务器；尚未提供 Unity / Unreal 连接适配器或引擎内插件。

## 使用流程

1. 保存「项目管理 → 工程连接」。首次准备协作入口与成员凭证可使用「项目启动」。
2. 在「同步配置」勾选「同步开发协作（任务与工具回写）」并保存。新配置默认开启；旧配置保持原有输出范围，需手动开启。
3. 预览并同步到工程。设计文档沿用配置目录；新素材在工程内制作，旧素材文件同步为可选兼容项，协作目录固定为工程内的 `gamecreator/`。
4. 开发者或 AI 阅读 `gamecreator/README.md`、上下文及设计文档。开始开发可提交进行中，完成实现建议提交待验收，并附开发结果、运行入口、验证情况和剩余问题。
5. 进入「开发反馈」自动读取待处理文件，并立即显示项目中已保存的处理记录。工程内新增文件后，可点击「读取开发反馈」刷新。查看导出时 / GameCreator 当前 / 开发反馈三列差异，冲突必须逐字段选择采用反馈或保留当前值。
6. 点击「应用反馈」或「忽略本条反馈」；也可使用「一键应用反馈」批量接收无冲突条目。应用后排期、工具、关联美术素材、剩余列表和记录计数自动刷新；忽略只记录处理决定，不修改目标字段。重新进入页签、重启客户端或工程读取失败时，已保存记录仍可查看。
7. 再次同步上下文，为下一轮开发提供最新基准。

## 协作目录

```text
gamecreator/
├─ README.md                     操作规范与可复制的反馈模板
├─ project-changes.md             需求建议与项目内容修改说明
├─ project.json                  项目 ID、引擎、当前快照、文档/素材目录
├─ context/
│  ├─ tasks.json                 任务、里程碑、依赖、验收要求及当前状态
│  ├─ tools.json                 开发工具需求与交付说明
│  ├─ content/<模块ID>.json       项目内容快照
│  └─ snapshots/<SHA-256>.json    已交付的历史比较基准
├─ feedback/
│  ├─ README.md
│  └─ <UUID>.json                每个文件一项任务、工具或模块的反馈
└─ receipts/
   ├─ README.md
   └─ <UUID>.json                应用/忽略结果与逐字段处理决定
```

`context/` 和 `project.json` 由 GameCreator 管理。反馈与回执文件不会进入向外同步的删除范围。关闭开发协作保留已生成内容，并仍可接收之前提交的反馈。历史快照用于比较旧反馈，不自动清理；文件重复同步内容一致时不产生虚假更新。

已有文档/素材目录不能占用 `gamecreator/` 或其子目录。协作目录是开发资料，发布时由项目自己的导出规则排除。`.gamecreator-sync/` 仍负责工程同步身份、备份和恢复记录，与开发反馈目录分工明确。

## 反馈协议 v1

文件使用 UTF-8 JSON，推荐先写 `.tmp`，完成后原子重命名为 `<id>.json`。每次新反馈使用新的小写 UUID。`projectId`、`engine`、`snapshotId` 复制自已同步的 `project.json`；目标 ID 取自 `tasks.json` 或 `tools.json`。

```json
{
  "schema": 1,
  "projectId": "复制工程中的项目ID",
  "engine": "godot-gdscript",
  "id": "3a807ea3-bdaf-490e-b7da-a381dcdff80c",
  "snapshotId": "复制工程中的64位快照哈希",
  "target": {"kind": "task", "id": "复制真实任务ID"},
  "author": "程序开发 / AI 助手",
  "summary": "骨骼动画预览实现完成，提交验收",
  "evidence": [
    "工具入口：debug/animation_preview.tscn",
    "已验证播放、暂停与逐帧；美术素材兼容性待验收"
  ],
  "changes": {
    "status": "待验收",
    "actualStart": "2026-09-22",
    "result": "已实现动画控制和事件轨道，等待美术样例验证"
  }
}
```

示例标识只是占位内容，必须复制当前工程中的真实标识。证据字符串仅显示为文字，不执行其中的命令，也不自动打开路径或网址。

| 目标 | 允许回写的字段 |
| --- | --- |
| `task` | `status`、`actualStart`、`actualEnd`、`result` |
| `tool` | `status`、`usage`、`delivery` |

任务状态：待开始、进行中、待验收、已完成、受阻。工具状态：待开发、开发中、待验收、可使用、停用。实际日期为有效 `YYYY-MM-DD` 或空字符串。`changes` 只填写本次修改的字段；未列出的字段原样保留。

采用“已完成”或“可使用”时必须勾选已核实交付与验收。应用任务反馈后，GameCreator 会按全部关联任务的完成情况同步工具验收；停用或归档工具保持原状态。素材按明确关联的美术任务同步制作进度，全部完成时标记已完成，无需导入或采用图片版本。素材交付路径、验证情况与未完成项写入任务 result，素材详情可直接查看。里程碑不会自动验收，任务全部完成后到项目排期点击确认。需求与验收要求通过 `spec_change` 提建议；具有 `project_write` 权限的项目范围长期开发者，可通过 `project_change` 修改已有内容和计划字段。人员授权与创建/删除条目仍在对应模块操作。详见 [需求与项目修改](project-change-feedback.md)。

## 一键应用

需求建议 `spec_change` 与正式项目修改 `project_change` 必须逐条评估并确认，不参与一键应用。顶部按钮显示本次可批量应用的数量。无冲突的进度与交付反馈可直接应用；涉及“已完成 / 可使用”的条目，勾选批量验收确认后一起纳入。字段冲突、同一目标的多条反馈及格式异常文件保留供逐条核对，不自动选择先后顺序，也不会写成“已忽略”。

批量按条目顺序保存，沿用单条反馈的归属、快照、文件变更和原子存档检查。同一模块连续处理时，只接受本批次自身产生的存档变化。遇到保存失败或外部修改，会停止后续条目，明确列出已应用、保留、失败的数量及原因；先前成功的条目保留处理记录，再次读取不会重复执行。

## 冲突、幂等与失败恢复

- 用稳定目标 ID 定位，任务改名不会断开关系。基准来自已交付、校验通过的历史快照，反馈不能自造比较基准。
- 当前值等于反馈值：显示一致，不再覆盖。当前值等于基准：可以更新。双方修改同字段且值不同：显示冲突。
- 其他字段发生变化时提示复核最新需求。合并后的实际起止日期也必须有效。
- 预览有效期十分钟。应用前检查活动项目、已保存工程连接、工程清单、反馈文件和目标存档，任何变化均要求重新读取。
- 项目、引擎不匹配，目标已删除或归档，未知字段、无效日期、损坏基准或链接路径都会阻止接收；单个无效反馈不影响其他合法反馈。
- 每次只应用一个目标。任务/工具反馈与记录保存在同一模块。正式项目修改跨越目标模块和排期记录时，使用本机恢复日志；中断后重新读取反馈完成已确认的保存。存在后续外部编辑时停止恢复，不覆盖外部编辑。恢复完成前阻止其他反馈应用和项目导出。
- 处理记录保存在对应模块的 `feedbackHistory` 中，随独立项目目录及项目导出保存。相同项目 ID 与更新 UUID 只处理一次；已处理文件被改写时要求新的 UUID。
- 工程 `receipts/` 是处理记录的镜像，不用于决定是否已经应用。写入失败时会提示“项目已保存”，在重启后点击“补写回执”可恢复，不重复修改目标。
- 单存档保存失败可重试；正式项目修改保存中断时先重新读取恢复，再继续处理。刷新不会覆盖当前模块尚未保存的草稿。
- 每个反馈和处理回执不超过 2 MB；每次最多读取 500 个 JSON 文件；每个模块最多保留 10000 条处理记录，且模块存档仍受 20 MB 限制。已处理反馈可移到 `feedback/` 之外自行归档；不会自动删除历史快照或幂等记录。

## 验证

运行 `npm run test:engine-sync` 和 `npm run build`。桌面回归为 `node tests/desktop-engine-feedback.cjs`，可通过 `GAMECREATOR_PLAYWRIGHT_PATH` 指定 Playwright。

测试使用临时工程和独立客户端配置，覆盖实际项目文件夹、上下文输出、三方字段冲突、验收选择、即时刷新、忽略记录、重复反馈、回执补写、保存失败、重启与窄窗口，不修改用户的游戏工程。


## AI 身份与分工

启用本地项目的“人员分配”后，工程会生成团队清单、成员工作说明和签名提交工具。AI 使用单独领取的凭证提交进度、验收结论或排期建议；读取和应用时都核对当前任务范围与权限。未签名旧反馈需逐条确认来源，不参与一键应用，无效签名不能绕过验证。详见 [AI 人员分配与凭证](ai-personnel.md)。
