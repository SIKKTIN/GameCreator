# 制作人管理 AI 开发团队

制作人负责从空项目建立设计、团队和制作计划，并根据引擎实际效果组织迭代。没有个人制作任务不代表无事可做。创建开发者身份和令牌后，把对应岗位工作文档与私有凭证交给实际 AI 助手；本功能不启动或控制外部 AI 会话。

## 更新协作文件在哪里

入口：左侧“项目管理 → 项目内容同步”，选择“设计提交”页签，点击页面上方的“更新协作文件”。

先在桌面客户端打开对应的 GameCreator 管理项目，并保存为独立项目文件夹。按钮不可用时，查看按钮下方提示，先完成保存、处理未保存内容或退出测试模式。

这一步更新管理项目根目录的使用说明、完整项目规范，以及 `ai/` 中的上下文、模板、校验与提交工具、团队管理说明和命令。它不会替你应用设计提交，也不会把引擎内的文档一起更新。

## 从授权到交给 AI 的操作顺序

1. 在“项目管理 → 人员分配 → 开发者与令牌”中编辑现有制作人，勾选“管理开发团队与令牌”，并选择项目范围。新建制作人默认拥有这项权限；其他权限按工作需要配置。已有长期身份授权后，原令牌继续使用，无需重新创建身份或更换令牌。
2. 到“项目管理 → 项目内容同步 → 设计提交”点击“更新协作文件”，刷新管理项目中的文档、公开授权和工具。
3. 在“项目管理 → 工程连接”保存引擎位置，随后进入“项目管理 → 工程同步”。在同步配置中开启“同步开发协作”和“同步成员凭证”，保存后预览并同步到工程，生成或更新引擎入口、成员工作说明以及 `personal/` 私有凭证。首次交付和后续更新使用同一入口；撤销、停用或更换令牌后检查待同步变更，旧凭证移除需明确确认。
4. 把引擎协作入口 README、对应成员工作说明和该成员自己的私有 JSON 凭证交给 AI。工作说明中的岗位职责、首轮行动和权限范围应一起阅读；不要只给一个令牌而省略工作入口。
5. 制作人沿引擎入口找到绑定的管理项目，阅读下方命令说明。运行团队管理命令期间，保持桌面客户端打开这个项目；后续人员、授权或项目内容变化后，再刷新协作文件与引擎文档。

软件内可随时通过“使用帮助 → 制作人与团队管理”阅读、复制或下载本说明，无需打开项目。更新协作文件后，同一份说明会生成在管理项目的 `ai/TEAM_MANAGEMENT.md`，命令脚本为 `ai/manage-team.cjs`。引擎开发仍在引擎项目中进行，团队管理命令从绑定的管理项目 `ai/` 目录执行。

## 使用前提

制作人使用自己的长期凭证 JSON 签名。岗位 `.md` 是工作说明，不是凭证。实际账号必须启用，岗位启用、令牌未撤销且未过期，范围为 `project`，并明确拥有 `team_manage`。新建制作人默认拥有；旧身份在“人员分配 → 开发者与令牌 → 编辑开发者”明确授权，不按名称自动升级。

`team_manage` 与 `project_write` 独立。团队管理只修改岗位、开发者资料、授权和任务分配，不改变任务完成状态、项目正文或验收结果。只能管理和授予自己拥有的权限、内容模块与素材专项能力，不能授予比自己更长的有效期。拥有素材模块完整写入权的管理者可以授予该模块的专项权限。自身授权由本地管理者调整。

## 读取团队并创建开发者

以下命令在管理项目 `ai/` 目录执行，要求 Node.js 22 或更新版本。凭证路径替换为引擎协作入口 `personal/` 中自己的 JSON 文件。

```sh
node manage-team.cjs status /私有位置/制作人.json
```

返回最新 `revision` 和 `schedule`，包含实际岗位 ID、任务 ID、成员、公开令牌与团队操作记录。创建 `create-program.json`，填入新 UUID、刚读取的 revision，以及真实岗位/任务 ID：

```json
{
  "id": "替换为本次操作的UUID",
  "operation": "create",
  "revision": "替换为status返回的revision",
  "input": {
    "name": "程序",
    "duties": "实现已确认的玩法与工程接入，提交运行验证及待验收反馈。",
    "permissions": ["progress", "spec_change"],
    "active": true,
    "profile": {
      "positionIds": ["program"],
      "taskIds": [],
      "scope": "positions",
      "expiresAt": "",
      "projectModules": [],
      "artPermissions": []
    }
  }
}
```

```sh
node manage-team.cjs run /私有位置/制作人.json create-program.json /引擎协作入口/personal/程序.json
```

命令直接完成创建与签发；凭证仅写入指定的**新文件**，不会打印私钥或覆盖已有文件。保存到凭证同步时已经排除 Git 和引擎资源导入的 `personal/` 中，不放入公共目录。此目录不提供各成员间的文件访问隔离。输出成员与令牌 ID。无任务可以创建，`taskIds` 支持多个任务，`positionIds` 支持兼岗。

## 后续管理

每次修改先读取 status，并核对最新状态；所有变更请求均使用新的 UUID 和最新 revision。每个请求只执行一种操作：

| operation | input | 效果 |
| --- | --- | --- |
| create | 上述完整资料；可加无当前令牌的 memberId | 创建或复用身份，签发长期令牌 |
| update | memberId + 完整 name/duties/permissions/active/profile | 修改职责、岗位、权限和多选任务，保留令牌 |
| rotate | memberId + credentialId + 完整资料 | 撤销旧令牌，签发新令牌；必须给新保存路径 |
| revoke | credentialId | 撤销令牌，保留身份和历史 |
| credential | credentialId | 重新导出未撤销凭证，必须给新保存路径；不需要 revision |
| position | id/name/duties/active/taskKinds | 新增或编辑岗位；不能修改制作人岗位 |

例如新增主美岗位：`input` 为 `{"id":"art-director","name":"主美","duties":"制定风格标准并验收游戏内视觉效果","active":true,"taskKinds":[]}`。之后创建该岗位开发者，可授予 `review` 和素材专项 `style/details/propose/dispatch`；全局 `propose`、内容模块写入按实际工作需要授予。现有任务的岗位归属不会因新增岗位自动改变。

分配工作时在 `update` 的 `profile.taskIds` 中填写完整任务清单；任务必须匹配所选岗位或使用已授予的项目范围。在“人员分配”和“任务清单”可查看工作分配。需要新增任务或调整设计时，用内容编写协议提交，待应用后再分配真实任务 ID。

超时后保留原请求文件，使用同一个编号重试。相同请求不会重复签发；同编号不同内容会被拒绝。若创建已完成但文件保存失败，可原样重试，或 status 找到令牌后使用 credential 重新导出。令牌已撤销时不能重新导出。客户端重启后等待本机入口更新，再运行命令。

操作记录与公开结果保存在项目排期人员数据中，与变更一起提交；私钥只保存在加密凭证库和明确指定的私有文件。状态变化后刷新协作文件与引擎文档，向成员交付最新工作说明。桌面人员列表会自动读取成功的外部操作；未保存的本地草稿保留并提示重新检查。

## 制作人的首轮交付

1. 阅读引擎入口、管理项目使用说明、规范与当前设计，检查已有工程效果和真实权限。
2. 空项目先明确体验目标、最小玩法循环、范围、不做内容、验收标准和风险；设计基本确定前不直接铺开程序实现。
3. 用项目编写协议建立必要的玩法、功能、素材文档、配置与排期，保持稳定 ID 和已有分类；不要复制整套模块制造版本分叉。
4. 按工作需要创建策划、程序、主美、美术、测试等身份，授予必要权限与任务。制作人可保持零个人任务。
5. 首轮汇报设计基线、团队职责及授权、任务依赖与验收、已提交/已应用状态和下一步。签名提交不等于已应用，制作完成不等于验收完成。
6. 开发中检查引擎表现与阻塞，推动反馈回写和规范兼容更新；收尾依据可运行结果、测试证据和里程碑标准组织验收。
