# 岗位、开发者与协作令牌

入口位于“项目排期”下方的“人员分配”，包含“岗位总览”“岗位任务”“协作令牌”“开发者与令牌”。岗位说明项目需要做什么；开发者代表持续参与项目的 AI 助手；令牌用于验证这个开发者提交的反馈。

## 日常使用

1. 在岗位总览维护制作人、策划、程序、美术、测试、音效等岗位的职责。岗位可以包含多个工作方向，任务也可以属于多个岗位。
2. 在协作令牌中命名开发者，也可以选择没有当前令牌的已有身份。选择岗位、职责、反馈权限与操作范围。
3. 具体任务为可选项。制作人可以选择项目范围和验收、建议权限，不指定制作任务；程序助手也可以先创建身份，再分配工作。
4. 生成成功后进入开发者与令牌页签。这里列出有效、停用、过期、撤销和属于原项目的所有令牌，可以筛选、重新复制完整凭证、下载凭证、编辑开发者或更换令牌。
5. 修改名称、职责、岗位、任务、权限或有效期时，原开发者 ID 和令牌不变。完成一批任务后继续使用同一开发者。
6. 在引擎设置开启开发协作并同步。将私有凭证单独交给对应 AI。开发者根据最新上下文提交签名反馈，在 GameCreator 中审核和应用。

任务详情和排期展示明确分配的开发者。项目范围是操作权限，不会将全项目任务自动计入制作人的工作量；岗位范围也不会把岗位全部任务算作个人任务。

## 范围与权限

| 操作范围 | 可提交反馈的工作 | 适用情况 |
| --- | --- | --- |
| 已分配任务 | 明确选择且仍属于开发者启用岗位的任务 | 指定分工；空任务时暂不能提交任务反馈 |
| 岗位范围 | 所选启用岗位的当前和后续任务 | 持续负责某个岗位 |
| 项目范围 | 当前项目内的任务及其关联工具 | 制作人、项目验收与统筹 |

范围与反馈权限分别配置。新建开发者时选择制作人岗位，会预选项目范围和项目修改权限；保存后的授权不随改名或更换岗位自动扩大。旧身份保留原权限：

- 制作进度 `progress`：提交开发结果、实际日期、进行中或待验收状态，不能直接标记已完成。
- 验收结论 `review`：提交验收结果；已完成或可使用仍须由 GameCreator 使用者核实接收。
- 排期与分配建议 `propose`：对任务提交建议，追加到建议记录，不覆盖任务结果和状态。
- 需求与验收变更建议 `spec_change`：建议修改任务说明和验收标准，必须说明原因与影响，管理者采纳后才修改正式内容。
- 项目内容修改 `project_write`：独立的项目权限，只供项目范围的长期开发者使用。提交 `project_change` 反馈，修改已有项目内容和计划字段；人员授权另行管理，进度与完成状态仍走验收流程。

后两种反馈逐条核对，不参与一键应用。详见 [需求与项目修改](project-change-feedback.md)。

长期令牌默认无到期日，也可设置到期日期。验证使用 GameCreator 中当前的成员启用状态、岗位、范围、权限、有效期及令牌撤销情况。读取、应用和最终保存反馈前都会复核。已复制出去的长期令牌不冻结旧权限，收回权限后旧凭证也不能继续使用被收回的能力。

## 私有凭证保管与恢复

新凭证由 Electron 主进程写入用户数据目录下的 `ai-credential-vault`，使用操作系统账户加密。普通项目存档、完整项目文件夹、设计文档与引擎同步只保存身份和公钥，不包含私钥。加密不可用时停止生成，不回退到明文保存。

同一用户数据目录下重启客户端后，可以再次复制或下载完整凭证。复制由主进程写入剪贴板；下载由用户选择文件位置。凭证文件单独交付给对应开发者，不应放入共享工程或版本库。跨机器、跨操作系统账户或删除用户数据后，需要导入此前下载的凭证备份，或更换令牌。

旧版本只在首次签发时提供私钥，无法从公钥还原。旧令牌没有本地凭证时，提供两个入口：

- 导入已保存凭证：核对项目、开发者、令牌 ID 和公私钥匹配后加密保存，以后可以反复复制。
- 更换令牌：复用同一开发者身份，保存新凭证成功后撤销选中的旧令牌。任务和反馈历史保留；其他历史令牌不会被自动撤销或合并。

卡片上的“删除令牌”会先确认，随后移除该令牌并清理本机加密凭证；有效和已撤销令牌均可删除。开发者身份、任务和反馈历史保留，同一开发者的其他令牌不受影响。删除后可在“协作令牌”中复用无当前令牌的已有身份重新签发。若清理或保存失败，令牌保留为已撤销状态，可重试删除。

已撤销的令牌不能继续分发。更换后需要重新交付新凭证。公共项目文件夹迁移只带公开记录，不能凭公开记录恢复私钥。

## 工程协作文件

```text
gamecreator/
├─ project-standards.md            通用规则与项目补充，更新前必读
├─ project-changes.md              需求建议与项目字段修改协议
├─ project.json
├─ context/
│  ├─ team.json                    岗位、开发者及公开验证信息
│  ├─ assignments.json             任务归属及明确分配
│  ├─ content/<模块ID>.json        16 个模块的可修改内容快照
│  ├─ tasks.json
│  └─ tools.json
├─ members/<开发者ID>.md            开发者工作说明
├─ assignments/<令牌ID>.md          当前范围、权限和已分配任务
├─ submit-feedback.cjs             签名提交工具
├─ feedback/                       开发者提交反馈
└─ receipts/                       GameCreator 处理回执
```

普通同步不生成新令牌。修改分工后重新同步，让开发者读取最新说明；最终授权始终由 GameCreator 当前存档决定。使用工程附带的新版签名工具：

```shell
node gamecreator/submit-feedback.cjs <私有凭证文件> <反馈草稿.json> gamecreator/feedback
```

辅助工具兼容旧凭证 schema 1 和长期凭证 schema 2。新凭证的到期时间不固化在文件中，由 GameCreator 校验。反馈签名不改变现有 JSON 协议，私钥不进入反馈。令牌只约束 GameCreator 接收的反馈，不控制外部 AI 的文件访问。

## 兼容与数据模型

排期仍为 schema 1，新增可选 `member.developer`，保存岗位 ID、明确分配的任务 ID、范围和有效期。`credential.persistent: true` 表示按当前开发者资料核验。一个开发者只生成一枚当前长期令牌；更换后的旧令牌保留用于追溯。

旧成员、负责人、任务分配、凭证和反馈不自动改写。旧凭证保留原来的任务与权限约束，不因打开页面或编辑开发者自动扩大范围；显式更换后才转为长期模式。复制项目时凭证仍绑定原项目，新项目需重新签发。未签名的历史反馈仍需逐条确认；无效签名不能跳过验证或批量应用。

## 项目岗位预设

岗位总览上方提供两套预设，选择后先展示岗位变化和任务归并预览，确认后按项目保存。旧项目继续使用基础协作，打开页面不会修改存档。

- 基础协作（6 岗位）：制作人、策划、程序、美术、测试、音效。
- 完整制作（8 岗位）：制作人、策划、主美、技术美术、美术开发、程序、测试、音效。

主美负责风格及游戏内视觉效果审核；技术美术负责制作技术、导入规格、性能与技术验收；美术开发按二者的规范制作和修改素材。审核与技术方案作为独立任务按需分配，不自动复制美术制作任务。一个开发者可以选择多个岗位；需要提交审核意见时，另行配置验收反馈权限。

完整制作沿用美术岗位 ID `art`，改用“美术开发”名称和职责。共同岗位的自定义名称、职责、任务方向与停用状态保持不变，自定义岗位保留；发生同名冲突时阻止切换并提示整理。预设是可修改的起点，不强制覆盖项目设置。

切回基础协作时，主美和技术美术任务归并到美术并去重；任务正文、状态、验收、依赖、成员和令牌不变。原岗位保留为停用记录，可勾选“显示停用岗位”查看。再次启用完整制作不推测任务原来的拆分，应按当前需求重新分配。

切换不会自动给开发者更换岗位授权或增加令牌权限。预览列出受影响的开发者与令牌，需到“开发者与令牌”核对授权。任务随归并出现在美术岗位范围内；只持有停用岗位的开发者不能借切换获得整个美术岗位的访问权。
