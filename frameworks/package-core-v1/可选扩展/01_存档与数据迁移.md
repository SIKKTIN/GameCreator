# 可选扩展：存档与数据迁移

[返回目录](../README.md)

## 1. 何时启用

当状态需要跨游戏运行、跨场景重新加载或作为检查点恢复时启用。单机完全可以使用本扩展，不需要客户端 / 服务端划分。

启用存档不要求引入中央 DataCore。数据可以继续由各 Package 持有，保存时提供快照，读取时按包恢复。

## 2. 两种合理起点

| 方式 | 适合 | 工作方式 |
| --- | --- | --- |
| 项目保存流程直接调用 | 包较少，保存规则稳定 | 明确调用各包导出和恢复方法 |
| 保存参与者注册 | 包较多，组合经常变化 | SaveCore 调度登记的保存参与者 |

注册仅用于发现保存入口，不意味着 SaveCore 接管所有运行时字段，也不要求每次修改都经过它。

## 3. 责任边界

| 责任 | 所有者 |
| --- | --- |
| 哪些字段需要保存、字段含义 | Package |
| 新档默认值、旧数据迁移、有效性验证 | Package |
| 存档槽位、读写调度、结果和备份 | 项目保存流程或 SaveCore |
| 真实文件或平台接口 | 当前环境的保存实现 |

业务快照不得包含引擎对象、函数、句柄或可被后续继续修改的共享引用。对象关系使用项目约定的稳定 ID。

## 4. 最小概念接口

```text
CaptureSaveData() -> 纯数据快照
PrepareRestore(version, data) -> 验证后的待恢复状态，或错误
ApplyRestore(preparedState) -> 应用已验证状态
CreateDefaultState() -> 新状态
```

这些是语义示例，具体方法可以合并或改名。恢复分成准备和应用，是为了在某个包校验失败时不让整个游戏只恢复了一半；若项目选择其他等效方案，需保证相同失败行为。

## 5. 存档结构示意

```json
{
  "formatVersion": 1,
  "projectId": "sample-game",
  "packages": {
    "planting": {
      "schemaVersion": 1,
      "data": { "plots": [] }
    },
    "inventory": {
      "schemaVersion": 1,
      "data": { "items": [] }
    }
  }
}
```

存档格式版本与包数据版本分别管理。文件格式、压缩、加密、云存档和槽位数由项目选择，不属于最小规范。

## 6. 保存流程

1. 选择一致的保存时刻，或冻结 / 复制本次保存涉及的状态快照。
2. 收集所有必需包的数据并验证可序列化性。
3. 使用当前存储实现写入，成功后更新有效存档记录。
4. 明确报告成功、失败或仅进入等待队列。

本地文件可按平台能力采用临时文件、替换与备份；需要检验实际平台保证。不能因为调用了写文件函数就宣称拥有跨文件事务或断电安全。

“已请求自动保存”和“已完成保存”是不同状态。游戏可以允许内存继续运行并重试保存，但界面与命令契约不能把未保存说成已保存。

## 7. 加载与迁移

```text
读取 → 识别项目与版本 → 迁移 → 校验全部必需数据
     → 应用恢复状态 → 恢复场景绑定 → 开放交互
```

- 新存档缺少整个包时，可以创建该包的默认状态。
- 已有包缺少字段时，使用明确迁移或兼容规则，不用默认初始化覆盖全部旧数据。
- 遇到更新的、不支持的存档版本时拒绝覆盖并报告不兼容。
- 迁移失败保留原始存档；迁移过程中不发奖、不触发普通玩法事件。
- 关闭可选包时按项目约定保留它的数据，不能在下一次保存时静默丢弃。
- 跨包迁移若有顺序依赖，应明确声明，并在全部准备成功后开放业务。

## 8. 验收

至少覆盖：新档、旧档、缺失包、非法数据、更新版本、保存失败、恢复失败、可选包重新启用。

要支持自动保存或多个保存任务时，还需验证旧保存不能晚到后覆盖新保存。项目没有并发保存需求时，可以先串行执行。
