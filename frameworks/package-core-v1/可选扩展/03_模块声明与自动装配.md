# 可选扩展：模块声明与自动装配

[返回目录](../README.md)

## 1. 何时启用

模块数量或组合增多、手工接入经常遗漏、需要自动检查依赖或生成目标引擎绑定时启用。

手工装配可以长期使用。声明文件、自动检查和代码生成是三个递进能力，可以只采用其中需要的部分。

## 2. 最小声明示例

```json
{
  "id": "planting",
  "description": "管理地块、浇水和生长规则",
  "dependsOn": []
}
```

格式可选 JSON、静态表或其他项目惯用方式。示例中的种植包不直接依赖背包，收获流程在上层组合二者，因此这里没有必需包依赖。

只有实际使用对应机制时，才增加版本、作用域、保存参与入口或可选集成信息。不要为了模仿绿洲 Meta，把 playerData / gameData 强制放进所有项目的包声明。

## 3. 声明与实际代码一致

依赖指包真正调用或导入的公共契约，不能只登记初始化顺序却漏掉运行时业务依赖。

若依赖信息同时存在于导入和清单中，应使用检查或评审发现不一致。声明解析不执行业务副作用；需要绑定函数时，在装配阶段完成，而不是通过启动业务来发现它。

## 4. 可选模块

- 必需依赖缺失时，拒绝装配依赖它的功能并给出原因。
- 可选集成缺失时，使用已经定义的无集成行为。
- 关闭模块不能静默删除数据或内容引用。
- 第一版可以只支持启动前配置，运行中切换另行设计。

业务模块是否可选与编辑器入口是否隐藏分别管理。隐藏界面不代表运行时数据已经卸载。

## 5. 生成行为

```text
源码 / 声明 / 项目选择
    → 校验
    → 计算启用模块与初始化顺序
    → 预览
    → 生成装配代码或固定索引
    → 编译与运行检查
```

生成目录可以继续叫 Setting，也可以叫 Generated。必须与业务 Config 区分，生成结果不手工添加逻辑。

同一输入产生稳定输出；不把每次变化的时间戳写入需要比较的结果。稳定 ID 不应因目录排序改变而重新编号，删除与重命名需要兼容策略。

生成失败时不发布半份有效索引。生成成功只代表装配结构通过相应检查，不能代替玩法测试。

## 6. 建议检查

缺失依赖、循环、引用私有模块、重复 ID、缺失绑定、禁用模块被必需引用，以及输出过期。

本目录没有提供这些检查器或生成器的实现。采用本扩展的项目应明确已实现的检查范围；动态调用和反射未被覆盖时，不能声称完成了全量依赖验证。

生成文件是否提交版本库由项目固定选择：构建可靠生成可不提交，构建依赖预生成结果则提交。两种情况都必须保证输入与结果一致。
