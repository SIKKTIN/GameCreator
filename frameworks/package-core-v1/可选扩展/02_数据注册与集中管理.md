# 可选扩展：数据注册与集中管理

[返回目录](../README.md)

## 1. 首先分清三件事

1. **Package 装配登记**：项目有哪些业务模块。
2. **保存参与者登记**：哪些业务参与存档，如何导出和恢复。
3. **集中运行时数据管理**：状态实际由统一后端持有，业务通过它读取和提交。

这三件事可以分别存在，不应因为用了一个就自动要求另外两个。

## 2. 何时值得统一管理运行数据

当多个业务确实需要同一种状态检查、调试观察、回放、变更追踪或提交机制时，可以评估集中管理。没有这些需求时，各包直接持有自己的状态通常更简单。

数据包和字段多，本身不等于必须使用中央字典。先判断已有语言类型、引擎对象或数据库是否已经满足需要。

## 3. 注册的最小内容

按用途选择以下信息，而不是全部必填：

| 信息 | 何时需要 |
| --- | --- |
| 稳定身份与业务拥有者 | 区分记录和责任 |
| 默认状态创建 | 管理器负责创建记录时 |
| 校验规则 | 后端统一接收状态写入时 |
| 保存导出与恢复 | 使用统一保存调度时 |
| 数据版本与迁移 | 需要持久化兼容时 |
| 调试展示 | 需要开发工具观察时 |

注册声明不应自动执行业务初始化、发奖或启动场景。调试格式化和数据迁移是不同责任，不能混用同一个回调。

## 4. 所有权保持不变

集中后端持有存储，并不获得业务解释权。Inventory 仍决定物品能否转移，Planting 仍决定作物是否成熟。

包外调用仍通过业务公共接口，不绕过业务直接用通用路径写入别人的字段。否则统一数据管理反而破坏了 Package 边界。

## 5. 避免双份权威状态

必须明确哪个表示是本次业务操作的事实来源：包内实例或统一后端。若存在缓存、视图或镜像，明确更新、失效和恢复规则。

不允许两个地方都独立修改同一业务状态，再依靠偶尔同步来保持一致。只读快照可以存在，但不得被当成可写主数据。

## 6. 接口必须说明的行为

- 查询返回内部引用、受控只读视图还是副本。
- 批量写入是全有或全无，还是逐项报告。
- 未变化、输入无效、版本冲突、目标缺失如何区分。
- 通知是在修改前、提交后还是保存后发出。
- 是否保存、何时保存；内存成功不默认等于持久化成功。
- 使用并发、异步或重入时如何防止覆盖新状态。

第一版可以只支持简单同步写入，不需要立即提供通用事务引擎。但必须如实说明其保证，不让调用者误以为失败会自动回滚。

## 7. 与绿洲数据模式的关系

PlayerController / GameState 宿主、蓝图属性、复制列表和 UGC 存档是特定接入方式，应放在绿洲补充中。

在单机项目中，集中后端可以只是本地对象，也可以完全不启用。不能为了复用原有 DataCore 接口人为制造“本地服务器”概念。
