# 通用游戏项目框架

> 版本：1.0 评审稿 · 更新日期：2026-09-21  
> 定位：以 Package / Core 为基础的游戏项目架构与开发规范。  
> 交付类型：文档框架，包含规则、目录模板和伪代码示例；不包含已经实现的运行时库、生成器或引擎插件。

这套框架规定业务如何组织、数据由谁负责、模块如何合作，以及如何验证结果。单机项目可以直接使用；引擎、语言、存档方式和网络模式由项目选择。

**基础规范不要求客户端 / 服务端划分，不要求集中数据注册，不要求统一 DataCore，不要求自动生成，也不要求建立完整引擎抽象层。**

## 1. 核心约定

1. **Package 拥有业务**：例如背包、种植、任务、战斗。它负责自己的规则、状态与公开行为。
2. **Core 提供公共机制**：只有真实需要统一管理的跨业务机制才进入 Core。简单工具函数可以独立存在。
3. **包外通过公开契约合作**：不直接读写其他包的私有状态，不依赖其内部目录。
4. **查询与修改职责明确**：Query 不改变可观察业务状态；命令明确说明结果、副作用和失败语义。
5. **数据与运行对象分开理解**：由业务决定数据含义，按需要选择存储与宿主，不预设特定引擎类。
6. **功能按需增加**：小项目可以手工装配、直接持有数据，只拆分有实际作用的目录和文件。

本框架中的 Registry 指“一个包的逻辑公共入口”，不是“中央数据注册表”。可使用 Registry、Facade、Service 或目标语言惯用命名。

## 2. 如何开始

首次阅读建议顺序：

1. [架构总纲](基础规范/01_架构总纲.md)：理解 Package / Core 的责任与边界。
2. [Package 组织与公共接口](基础规范/02_Package组织与公共接口.md)：建立第一个业务包。
3. [数据与配置](基础规范/04_数据与配置.md)：确定数据所有权与读写方式。
4. [最小项目结构](示例/02_最小项目结构.md)：按实际复杂度搭建目录。
5. [单机种植与背包](示例/01_单机种植与背包.md)：查看完整交互与失败处理。

开始实现时，只需要选择一个业务、定义公开行为、在项目入口装配并验证结果。不必先实现所有 Core 或所有扩展。

## 4. 基础与扩展的关系

| 项目情况 | 推荐起点 | 暂不需要 |
| --- | --- | --- |
| 无存档单机原型 | Package、公开接口、直接数据、手工装配 | 网络、保存注册、生成器 |
| 有存档单机游戏 | 基础 + 存档扩展 | 客户端 / 服务端、复制字段 |
| 多团队大型工程 | 基础 + 按需声明、检查或集中机制 | 未必需要网络，也未必需要统一数据后端 |
| 多人游戏 | 基础 + 联机扩展 + 对应引擎接入 | 没有需求的复杂预测、回滚和跨服能力 |
| 绿洲启元现有项目 | 基础 + 绿洲补充，保留兼容实现 | 不需要为了“通用”立即重写已验证代码 |

可选扩展彼此独立。启用存档不等于启用中央数据管理，使用元数据不等于必须代码生成，使用本地事件不等于需要网络传输。

## 5. 阅读规则

- “必须 / 不得”只在所属能力启用且相关场景存在时适用。
- “建议”允许项目根据复杂度调整，调整理由记录在项目说明中。
- 示例中的接口和目录是模板，不是已存在的 API，也不是必须采用的名字。
- 各文档讨论通用职责；具体语法、引擎对象、资源格式和版本放在项目或引擎补充中。
- 本目录是新的通用规范。此前《多引擎游戏项目框架设计方案》作为分析与扩展参考保留，不作为本基础规范的隐含必选要求。

## 6. 最小采用声明

项目可以在自己的 README 中记录：

```text
采用规范：通用游戏项目框架 1.0
引擎与语言：由项目填写具体版本
运行模式：单机
业务包：种植、背包
公共机制：直接使用引擎日志；其他按需
状态持有：各业务包自己的实例
装配方式：项目入口手工装配
可选扩展：无
项目例外：无，或列出实际差异
```

本规范不规定 Git 分支命名、提交方式或发布权限，沿用项目已有协作约定。
