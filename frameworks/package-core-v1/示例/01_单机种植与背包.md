# 示例：单机种植与背包

[返回目录](../README.md)

## 1. 范围

本例是伪代码和行为契约，不是可直接运行的某种语言实现。游戏支持地块种植、浇水、按游戏日生长以及收获进入背包。

默认离线、单次会话、同步操作。没有服务器、网络复制、中央数据注册或自动装配。存档在最后单独增加。

## 2. 业务划分

| 部分 | 责任 | 不负责 |
| --- | --- | --- |
| Planting | 地块、浇水、生长、成熟与收获规则 | 背包存储、具体 UI |
| Inventory | 物品容器、容量、堆叠与增加规则 | 作物何时成熟 |
| HarvestFlow | 协调收获与入包这个完整操作 | 直接修改两包私有字段 |
| 项目入口 | 创建实例、绑定输入、推进游戏日 | 各种作物的规则判断 |
| UI / 场景 | 显示地块、发送操作、反馈结果 | 直接给地块或背包字段赋值 |

HarvestFlow 可以是一个小函数或业务文件；只有流程规模扩大后才考虑独立编排包。

## 3. 私有数据

```text
Planting 私有状态：
  plots[plotId] = { cropId, growthDays, wateredToday, harvested }

Inventory 私有状态：
  items[itemId] = count
  capacity

作物配置：
  cropId, requiredGrowthDays, harvestItemId, harvestCount
```

配置可由代码定义或外部文件读取，并在使用前校验。每个包创建独立状态实例，不把进度写入配置，也不把内部可变表交给 UI。

## 4. 最小装配

```text
cropRules = LoadAndValidateCropRules()
inventory = CreateInventory(capacity)
planting = CreatePlanting(cropRules)
harvestFlow = CreateHarvestFlow(planting, inventory)
BindScene(planting, harvestFlow)
```

`LoadAndValidateCropRules` 等只是语义名称。可以直接调用项目函数，不需要实现一个配置 Core 才能开始。

## 5. 查询与浇水

```text
GetPlotView(plotId):
  找不到地块 → 返回 PlotMissing
  找到地块 → 返回界面需要的值快照

Water(plotId):
  找不到地块 → 返回 PlotMissing
  地块不可浇水 → 返回 NotWaterable
  今天已经浇水 → 返回 AlreadyWatered，不改变状态
  否则设置 wateredToday = true
  返回 Watered
```

本例浇水不消耗背包资源。若增加水量消耗，需明确整体操作失败语义并协调相关拥有者，不能在 UI 中先扣水再直接改地块。

只有当前界面需要立即更新时，可以根据返回值重新查询。多个系统需要响应时，再增加事实通知。

## 6. 游戏日推进

本例选择“每个完成的游戏日结算一次”，不依赖真实帧率：

```text
AdvanceDay(dayId):
  dayId 已结算 → 返回 AlreadyApplied
  遍历需要生长的作物
  按规则根据 wateredToday 推进 growthDays
  清除当天浇水状态
  记录已结算 dayId
  返回变化摘要
```

dayId 的来源和结算触发由项目时间流程确定。保存功能启用后，结算身份和相关进度也要按实际规则保存，防止读档重复结算。

## 7. 收获与入包

必须满足：未成熟或背包容量不足时，不移除作物，也不增加物品。不能先清空作物，再发现背包装不下。

### 7.1 本例采用的同步契约

两包提供只读的准备接口，分别校验并生成内部认可的操作计划。准备不修改状态，不触发回调。随后在同一个同步、无重入片段中提交两份计划，再刷新界面或发布通知。

```text
TryHarvestToInventory(plotId):
  harvestPlan = Planting.PrepareHarvest(plotId)
  harvestPlan 失败 → 返回对应结果

  addPlan = Inventory.PrepareAdd(harvestPlan.item, harvestPlan.count)
  addPlan 失败 → 返回对应结果，两包均未变化

  在无等待、无外部回调的片段中：
    Planting.ApplyPreparedHarvest(harvestPlan)
    Inventory.ApplyPreparedAdd(addPlan)

  此时才公开成功通知
  返回 Harvested
```

计划由拥有者产生和校验，协调者不写内部字段。提交阶段不再执行可能出现预期业务拒绝的操作，不调用磁盘、资源加载或网络，也不在第一步提交时通知外部监听者。

### 7.2 适用限制

这段流程依赖同步、无并发修改、无重入、提交前完成预期失败验证。它不是通用事务引擎，也没有承诺崩溃恢复或任意程序异常下自动回滚。

如果实际实现中的提交可能出现其他可恢复失败，应增加快照补偿或更明确的提交单元后再承诺整体失败不变；如果引入异步和并发，需增加预留或版本校验。不能只捕获异常并返回“失败”，却留下单边修改。

对小项目也可以采用其他简单且能证明一致性的流程，但必须通过相同验收案例。

## 8. 按需增加存档

项目保存入口调用 Planting 和 Inventory 的快照导出，写入一份当前会话存档。两个包仍持有自己的状态，不必迁入中央字典。

需要恢复时，先验证两份数据，全部准备好后应用，再重建场景绑定。保存涉及的同一收获过程不得只捕获一半状态。

## 9. 验收案例

| 情况 | 预期 |
| --- | --- |
| 合法浇水 | 只有目标地块变为已浇水 |
| 同一天重复浇水 | 状态不再改变，返回可区分结果 |
| 重复结算同一游戏日 | 不重复生长 |
| 未成熟收获 | 作物与背包都不改变 |
| 背包不足 | 作物与背包都不改变 |
| 正常收获 | 作物完成收获，背包增加正确物品数量 |
| 重复收获 | 不重复获得物品 |
| 两个独立游戏实例 | 数据互不影响 |
| 场景重新绑定 | 不重复注册输入，不意外重建会话数据 |
| 开启存档后恢复 | 两包状态一致，不能重复结算或重复收获 |

这些案例可以在不同引擎中重用，具体场景节点、对象和语法可以不同。
