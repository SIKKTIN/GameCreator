# 示例：最小项目结构

[返回目录](../README.md)

所有路径都是逻辑模板。实际文件扩展名、程序集、资源目录与引擎工程布局按项目调整，不要求照搬一套 Script 目录。

## 1. 两个业务包的起点

```text
项目/
  README.md
  Entry/                        # 项目装配和运行入口
  Packages/
    Planting/
      README.md
      Planting.<ext>            # 公开方法及私有实现
    Inventory/
      README.md
      Inventory.<ext>
  Gameplay/
    HarvestFlow.<ext>           # 上层收获协调
  Presentation/                 # 场景、UI 和输入绑定
  Tests/                        # 按测试框架实际位置放置
```

不必预先创建 Core、Meta、Generated 或 Network 空目录。引擎已经有合适日志、时间或事件能力时，可以直接使用。

## 2. 包复杂后再拆

```text
Packages/Planting/
  README.md
  Public/
    PlantingApi.<ext>
    PlantingResults.<ext>
  Query/
    PlotQueries.<ext>
  System/
    Watering.<ext>
    Growth.<ext>
    Harvest.<ext>
  Data/
    PlotState.<ext>
    CropDefinition.<ext>
    CropValidation.<ext>
```

调用方仍然使用公开接口，内部拆分不应要求所有调用方改为直接引用 System。没有对应复杂度就不拆。

## 3. 公共机制出现后

```text
Core/
  Save/                         # 需要统一保存调度时
  Diagnostics/                  # 引擎原生能力不足时
Config/
  Planting/                     # 需要策划编辑或外部覆盖时
```

文件夹存在不代表所有包都必须依赖它。Save 也不接管所有包的运行状态。

## 4. 装配扩展启用后

```text
Packages/Planting/
  package.manifest.json         # 选择声明机制后才新增
Bindings/                       # 实际实现与清单之间的绑定
Tools/                          # 已实现的检查或生成工具
Generated/                      # 或沿用项目既有 Setting 名称
```

项目 README 记录生成入口、输入、输出、检查范围和生成文件提交策略。没有实现的工具不应写成“运行后自动完成”。

## 5. 引擎目录

引擎原生资源、场景、预制体、蓝图、脚本和导入配置按各引擎惯例保存。框架可以使用命名空间、资源分组或约定表达职责，不要求额外包一层同名文件夹。

只需要当前引擎的接入实现，不在一个小项目中预建所有其他引擎的空目录。

## 6. 文档同步

项目根 README 写实际采用的能力；包 README 写职责与接口。框架版本更新不自动修改已有项目，涉及接口和数据变化时按项目自己的流程迁移并验证。
