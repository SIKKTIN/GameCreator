# 从原 PackageGuider 迁移

[返回目录](README.md)

## 1. 目标

保留 Package / Core、公共入口、业务所有权、显式依赖等已有价值，将特定引擎和可选机制从基础必选规则中移出。

迁移不要求立即替换 DataCore、删除 Meta、改存档键或重写工具。本目录是新的规范文件夹，没有执行任何项目代码迁移。

## 2. 对照表

| 原规范内容 | 新规范处理 |
| --- | --- |
| Package / Core 分工 | 保留，强调实际业务与机制边界 |
| Registry 作为公共门面 | 保留逻辑边界，名称和语言形式可调整 |
| Query / System / Data | 保留职责，目录按复杂度选用 |
| Define / Config / Const | 保留区别，不强制全部外置或全局化 |
| Event 表达事实 | 保留，事件机制可按需采用 |
| 所有 Package 必有 Meta | 调整为声明与装配扩展，简单项目可手工装配 |
| PlayerData / GameData 注册 | 移至数据管理和绿洲接入说明 |
| 数据固定挂 PlayerController / GameState | 仅作为原引擎宿主约定 |
| 所有修改集中经 DataCore | 作为集中管理选项，允许包直接持有状态 |
| 服务端校验与复制字段 | 移至联机与对应引擎扩展 |
| GenKit / Setting | 保留可用工具；生成装配不再是所有项目的前置条件 |
| AutoTestKit / DebugKit | 保留项目实现，提取通用测试与诊断要求 |
| 禁止引擎等价中间层 | 保留避免无意义转发的目的，允许有实际需要的适配 |

## 3. 新项目采用步骤

1. 写清引擎、语言、游戏运行模式和当前功能范围。
2. 确定最小业务包及其公开行为。
3. 采用最直接的状态持有和装配方式。
4. 验证一条完整玩家操作流程。
5. 根据出现的实际需求启用扩展，记录理由与保证。

纯单机项目从这里开始即可，不需要先阅读和实现绿洲数据规范。

## 4. 已有绿洲项目迁移步骤

### 第一步：记录现状

列出已有 Package、Core、数据键、宿主字段、保存链路、复制关系和工具生成文件。依据真实代码确认，而不是只依据规范描述推断。

### 第二步：只整理文档边界

把引擎要求、网络要求和项目历史兼容逻辑标明。已验证运行行为保持稳定，不因更换文档就删除检查或字段。

### 第三步：从一个低风险业务切入

选择边界明确的包，收紧公共接口和私有状态访问。已有 DataCore 可以继续作为内部存储实现，调用方不需要知道它是否已经替换。

### 第四步：按需调整机制

确认需要独立保存入口、纯规则测试或第二引擎运行后，再逐步拆分绑定。旧数据结构有变化时先准备迁移和回归样本。

### 第五步：验证与收敛

验证业务结果、旧档和必要网络行为；再删除已无调用的旧入口。生成文件通过现有工具更新，避免手工改生成区产生双份事实来源。

## 5. 不能机械执行的调整

- 不能仅把 PlayerData 重命名为 LocalData 就认定已经脱离引擎。
- 不能删除服务端校验却继续接收原有网络请求。
- 不能取消集中管理却同时保留两份独立可写状态。
- 不能改 dataKey 后让旧存档静默丢失。
- 不能把已有的自动生成职责移除后漏掉手工装配。

## 6. 与上一份设计方案的关系

此前《多引擎游戏项目框架设计方案》包含统一状态后端、Authority、元数据生成和跨包提交等较完整的扩展方向。

本目录按本次讨论收敛基础要求：这些能力只在需要时采用，不作为开始开发的门槛。单机项目无需实现 Authority 抽象、网络角色或中央 DataCore 才能符合本框架。

两份资料有表达差异时，当前这套通用规范的“基础与可选”划分作为本目录的采用依据；项目已有行为与实际迁移仍需独立评估。

## 7. 验收目标

能用少量文件实现一个遵循业务边界的单机功能；增加存档或网络时能定位新增责任；已有引擎项目迁移时能保持数据和已验证行为。这三件事比目录名字完全统一更重要。
