# Package 组织与公共接口

[返回目录](../README.md)

## 1. 最小要求

每个包应能够回答：负责什么、不负责什么、如何调用、持有哪些状态、依赖谁、何时创建和释放。

最小逻辑组成只有职责说明、公共入口和实现。文件可以合并，不要求必有 Meta、Data、Query、System 或 Tests 目录。

```text
Packages/Planting/
  README.md
  Planting.<语言扩展名>     # 简单包可在一个文件中实现公开方法和私有状态
```

## 2. 规模增长后的拆分

```text
Packages/Planting/
  README.md
  Public/                  # 公开入口、结果类型和事件契约
  Query/                   # 只读查询
  System/                  # 修改与业务流程
  Data/                    # 私有状态、结构、默认值和校验
  Tests/                   # 或放在项目统一测试目录
```

按需增加目录。`System` 在这里表示业务操作实现，不要求采用 ECS，也不意味着所有 System 每帧执行。Model、Handler 等名称只在项目确有对应责任时使用。

## 3. 公共入口

Registry / Facade 代表一个逻辑边界，不强制一个巨大文件。公开类型可以由多个文件提供，但调用方不需要知道包内部 Query 和 System 的目录。

公开方法需要说明：

| 信息 | 示例 |
| --- | --- |
| 作用对象与输入 | Water(plotId) |
| 结果 | 已浇水、已经浇水、地块不存在、不能浇水 |
| 数据影响 | 修改所选地块的浇水状态 |
| 失败状态 | 本命令失败时不改变地块 |
| 同步性 | 本例同步执行 |
| 生命周期前提 | 当前种植实例已创建且未释放 |

语言支持静态类型时优先使用类型检查。不为了统一接口而把所有方法改成字符串名、任意字典和运行时反射。

## 4. Query 与命令

```text
Planting.GetPlotView(plotId)     # 查询：返回展示需要的值
Planting.Water(plotId)           # 命令：执行规则并返回结果
```

Query 可以有不影响业务的内部缓存，但不得发奖、推进时间、修改任务进度或把查询当作初始化玩家状态的隐蔽入口。

命令先验证再修改。若命令允许部分完成，必须明确返回实际完成范围；不允许出现“返回失败但调用方不知道已经扣了部分资源”的行为。

## 5. 数据边界

- 包可以直接持有自己的实例状态，不必中央注册。
- 返回集合时使用值、只读视图或快照，避免调用者通过引用绕过接口写入。
- 高性能路径可以采用受控只读借用等语言机制，但要明确寿命和禁止修改规则。
- 包内部字段名不是天然公共协议；存档与网络需要时另行定义稳定表示。

## 6. 包之间合作

允许 A 直接依赖 B 的公开接口，例如 Planting 在需要容量信息时查询 Inventory。依赖通过构造、初始化参数或明确的语言模块导入体现。

当一个操作同时协调多个独立包且放在任何一方都会形成循环时，可由更上层的业务流程协调。例如“收获作物”流程明确调用 Planting 和 Inventory。小项目可以是一个清晰函数，不必立刻建立一个大型编排框架。

协调者也不拥有参与包的内部数据，不能替它们直接写字段。

## 7. README 建议模板

```text
职责：
不在范围内：
公共查询：
公共命令及结果：
私有数据与有效范围：
依赖：
创建与释放：
可选扩展：
关键验收案例：
已知限制：
```

没有存档、事件或更新需求时，直接写“不使用”，不创建空文件占位。
